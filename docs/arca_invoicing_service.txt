# Módulo ARCA multi-tenant

Guía de configuración, validación, APIs, facturación automática, emisión explícita y operación.

Última actualización: 2026-07-28.

## 1. Objetivo y alcance

El módulo permite que cada tenant configure credenciales fiscales independientes para homologación y producción, y emita comprobantes electrónicos mediante ARCA/WSFE.

La solución está dividida entre dos servicios:

- `postas_api`: API pública, permisos de usuario, configuración del tenant, ventas y outbox transaccional.
- `postas_platform_api`: fuente de verdad fiscal, perfiles cifrados, entitlement, facturas, correlatividad, conexión con Afip SDK/ARCA y worker de emisión.

El frontend nunca selecciona el tenant fiscal, el CUIT emisor, el ambiente real ni las credenciales utilizadas para emitir. Esos datos se derivan del JWT y de la configuración persistida para el tenant.

## 2. Arquitectura

```text
Cliente / frontend
       |
       | JWT del usuario
       v
postas_api
  - TenantConfig
  - Sale / SaleDetail
  - arca_fiscal_outbox
       |
       | HTTPS
       | X-Postas-Source: postas_api
       | X-Postas-Service-Token: <token interno>
       v
postas_platform_api
  - billing / entitlement arca_invoicing
  - arca_fiscal_profiles
  - arca_invoices
  - arca_invoice_items
       |
       | cert + key + access_token + CUIT + environment
       v
app.afipsdk.com -> WSAA / WSFE de ARCA
```

Procesos independientes:

1. API de `postas_api`.
2. Worker `python manage.py run_arca_outbox_worker`.
3. API de `postas_platform_api`.
4. Worker `python -m app.arca.worker`.
5. PostgreSQL compartido por la API y el worker de cada servicio.

Los workers fallan cerrados si su conexión no usa PostgreSQL. Esto es necesario porque el circuito utiliza `FOR UPDATE SKIP LOCKED` y, en Platform, advisory locks para proteger la numeración fiscal.

## 3. Conceptos importantes

### 3.1 Tenant

Todo perfil y toda factura pertenecen a un `tenant_id`. En la API pública el tenant sale exclusivamente del JWT (`request.tenant_id`). Un `tenant_id` enviado en el JSON del cliente no participa del circuito.

### 3.2 Ambientes

Valores admitidos:

- `development`: homologación/testing.
- `production`: producción.

Cada tenant puede mantener un perfil distinto para cada ambiente. Certificado, clave, token, punto de venta y tipo de comprobante pueden ser diferentes.

El ambiente se copia al snapshot de la outbox cuando se confirma la venta. Cambiar luego `TenantConfig.arca_environment` no mueve solicitudes existentes entre ambientes.

### 3.3 Credenciales y configuración fiscal

Secretos cifrados:

- `certificate`: certificado X.509 PEM de ARCA.
- `private_key`: clave privada PEM correspondiente al certificado.
- `access_token`: token de Afip SDK para `app.afipsdk.com`.

Configuración no secreta:

- `arca_cuit`: CUIT representado, 11 dígitos.
- `point_of_sale`: punto de venta habilitado para Web Services.
- `automatic_voucher_type`: código de comprobante que se utilizará.
- `concept`: `1` productos, `2` servicios o `3` productos y servicios.
- `default_vat_rate`: alícuota usada para separar neto e IVA desde precios finales.
- `default_vat_id`: identificador de alícuota enviado a WSFE.

El tipo de comprobante debe corresponder a la condición fiscal del emisor y del receptor. Por ejemplo, un responsable inscripto suele emitir comprobantes clase B a consumidor final, mientras que un monotributista o exento emite clase C. El código no infiere esta condición: el OWNER debe configurar el código correcto.

### 3.4 Entitlement

La feature booleana es `arca_invoicing`.

- Habilitada inicialmente: `business`, `business_ai` y `test`.
- No habilitada inicialmente: `free` y `starter`.
- `custom`: configuración manual mediante billing.

Se comprueba al configurar credenciales, rotar el keyring, activar automatización y crear facturas.

## 4. Requisitos previos en ARCA y Afip SDK

Antes de configurar un tenant se necesita:

1. CUIT representado.
2. Clave privada usada para generar el CSR.
3. Certificado X.509 emitido por ARCA para esa clave y CUIT.
4. Web Service de Factura Electrónica autorizado para el certificado/representado.
5. Punto de venta habilitado para Web Services en el ambiente correspondiente.
6. `access_token` de Afip SDK.
7. Código de comprobante compatible con la condición fiscal.

Afip SDK recibe `CUIT`, `cert`, `key`, `access_token` y `production`. En este módulo `production` se deriva del ambiente; nunca se recibe desde el frontend.

## 5. Configuración de infraestructura

### 5.1 Dependencias de Platform

La dependencia fiscal está fijada en:

```text
afip.py==1.2.0
```

También se utilizan `cryptography` para X.509/Fernet y `psycopg` para PostgreSQL.

### 5.2 Variables de `postas_platform_api`

| Variable | Obligatoria | Valor recomendado / función |
| --- | --- | --- |
| `DATABASE_URL` | Sí fuera de Compose | DSN SQLAlchemy. Para el worker debe ser PostgreSQL. |
| `PLATFORM_DATABASE_URL` | Opcional | Override del DSN utilizado por Docker Compose. |
| `POSTAS_SERVICE_TOKEN` | Sí | Secreto compartido con `postas_api`; sin valor la API interna responde `503`. |
| `POSTAS_SERVICE_TOKEN_HEADER` | No | Debe permanecer `X-Postas-Service-Token` para el cliente actual. |
| `POSTAS_SERVICE_SOURCE_HEADER` | No | Debe permanecer `X-Postas-Source`. |
| `ALLOWED_REQUEST_SOURCES` | Sí | Debe incluir `postas_api`; sin lista la API falla cerrada. |
| `POSTAS_INTERNAL_REQUIRE_TLS` | Sí en producción | `true` exige que ASGI vea la request como HTTPS. |
| `ARCA_CREDENTIAL_MASTER_KEYS` | Sí para usar ARCA | Objeto JSON `key_id -> Fernet key`. No existe fallback. |
| `ARCA_CREDENTIAL_ACTIVE_KEY_ID` | Sí para usar ARCA | Identificador usado para nuevas escrituras y rotaciones. |
| `ARCA_PRODUCTION_CALLS_ENABLED` | No | `false` por defecto. Debe habilitarse explícitamente para producción. |
| `ARCA_TIMEOUT_SECONDS` | No | Timeout de red hacia Afip SDK; default `30`. |
| `ARCA_WORKER_POLL_SECONDS` | No | Espera del worker sin trabajo; default `5`. |
| `ARCA_WORKER_BATCH_SIZE` | No | Cantidad máxima por ciclo; default `20`. |
| `ARCA_CONSUMER_FINAL_IDENTIFICATION_THRESHOLD` | No | Umbral implementado; default `10000000`. Revisar ante cambios normativos. |

Ejemplo sin secretos reales:

```env
DATABASE_URL=postgresql+psycopg://postas_platform:password@postgres:5432/postas_platform
POSTAS_SERVICE_TOKEN=<secreto-largo-y-aleatorio>
POSTAS_SERVICE_TOKEN_HEADER=X-Postas-Service-Token
POSTAS_SERVICE_SOURCE_HEADER=X-Postas-Source
ALLOWED_REQUEST_SOURCES=postas_api
POSTAS_INTERNAL_REQUIRE_TLS=true

ARCA_CREDENTIAL_MASTER_KEYS={"2026-07":"<fernet-key-base64>"}
ARCA_CREDENTIAL_ACTIVE_KEY_ID=2026-07
ARCA_PRODUCTION_CALLS_ENABLED=false
ARCA_TIMEOUT_SECONDS=30
ARCA_WORKER_POLL_SECONDS=5
ARCA_WORKER_BATCH_SIZE=20
ARCA_CONSUMER_FINAL_IDENTIFICATION_THRESHOLD=10000000
```

Generar una Fernet key:

```powershell
.\env\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

La salida debe almacenarse en el secret manager del ambiente. No debe versionarse en `.env.example`, Dockerfile, Compose, logs ni documentación.

## 6. Validaciones necesarias

### 6.1 Validación del keyring

Al cifrar o descifrar se valida:

- `ARCA_CREDENTIAL_MASTER_KEYS` existe.
- Es un objeto JSON no vacío.
- Todos los IDs y valores son strings.
- Cada valor es una Fernet key válida.
- `ARCA_CREDENTIAL_ACTIVE_KEY_ID` existe dentro del keyring.
- La clave histórica requerida para descifrar sigue disponible.

Errores típicos:

- `credential_keyring_unavailable` con HTTP `503`.
- “La clave requerida para descifrar las credenciales no está disponible”.

### 6.2 Validación criptográfica local

Antes de persistir el perfil:

1. El certificado debe ser X.509 PEM válido.
2. La clave debe ser PEM válida y no puede estar protegida con contraseña.
3. La clave pública derivada de la private key debe coincidir con la del certificado.
4. El certificado debe estar vigente: no futuro y no vencido.
5. El certificado debe informar un `SERIAL_NUMBER` con el CUIT.
6. El CUIT informado debe coincidir con el certificado.
7. Certificado, clave y token no pueden estar vacíos.

Los tres secretos se cifran antes del commit. Las respuestas sólo exponen huella SHA-256, vencimiento e ID de clave.

### 6.3 Validación fiscal live

Después del `PUT` del perfil, `postas_api` solicita inmediatamente la validación de Platform. Platform crea el cliente Afip SDK y ejecuta una consulta de última correlativa para el punto de venta y tipo configurados.

Esa llamada comprueba en conjunto:

- Descifrado de los tres secretos.
- Validez del `access_token` de Afip SDK.
- Obtención/reutilización del Ticket de Acceso de WSAA.
- Relación entre certificado y CUIT representado.
- Autorización para WSFE.
- Existencia/acceso al punto de venta y tipo de comprobante.
- Conectividad con el ambiente seleccionado.
- Guard de producción.

Resultado válido:

```json
{
  "valid": true,
  "status": "valid",
  "error": null
}
```

Resultado inválido:

```json
{
  "valid": false,
  "status": "invalid",
  "error": "ARCA rechazo las credenciales configuradas."
}
```

Errores de provider son sanitizados: no se devuelven PEMs, bearer tokens ni `access_token`.

### 6.4 Validación de billing

`arca_invoicing` debe estar habilitada para el tenant. Si no lo está, no se permite:

- Configurar o reemplazar credenciales.
- Validar o rotar el perfil.
- Activar facturación automática.
- Encolar una factura explícita o correlativa.

### 6.5 Validación de producción

Para emitir o validar `production` deben cumplirse ambas condiciones:

1. Existe un perfil `production` válido para el tenant.
2. La instancia tiene `ARCA_PRODUCTION_CALLS_ENABLED=true`.

Tener credenciales productivas guardadas no habilita por sí solo llamadas productivas.

### 6.6 Validación de permisos y tenant

API pública:

- Configuración: sólo `OWNER`.
- Crear factura siguiente o explícita: cualquier usuario autenticado.
- Consultar por `external_id`: emisor original, `ADMIN` u `OWNER`.
- Consultar referencia fiscal o última correlativa: `ADMIN` u `OWNER`.

Si se informa `sale_id`, la venta debe pertenecer al tenant del JWT. El actor se reemplaza por `request.user.uuid` y `request.user.role`.

API interna:

- `POSTAS_SERVICE_TOKEN` configurado.
- `ALLOWED_REQUEST_SOURCES` configurado.
- `X-Postas-Source` permitido y, para ARCA, exactamente `postas_api`.
- `X-Postas-Service-Token` válido mediante comparación constante.
- HTTPS cuando `POSTAS_INTERNAL_REQUIRE_TLS=true`.

### 6.7 Validación del perfil para emitir

- Perfil existente para `(tenant_id, environment)`.
- `validation_status == "valid"`.
- Entitlement habilitado.
- Automática: sólo `concept == 1`.
- Concepto `2` o `3`: requiere `service_start_date`, `service_end_date` y `payment_due_date`.
- No se puede reemplazar o eliminar un perfil con facturas no terminales.
- `upsert`, `delete` y `enqueue` bloquean la fila del perfil con `FOR UPDATE` para evitar carreras.

### 6.8 Validación de factura

- `external_id`: requerido, no vacío, máximo 160 caracteres.
- `sale_id`: UUID opcional.
- `items`: al menos uno.
- Descripción: 1 a 255 caracteres.
- Cantidad: positiva, hasta 4 decimales.
- Precio final unitario: no negativo, hasta 2 decimales.
- Documento: sólo dígitos, máximo 20 caracteres.
- Las tres fechas de servicio se informan juntas.
- Fecha inicial de servicio no posterior a la final.
- Número explícito positivo.

Idempotencia:

- Unicidad `(tenant_id, external_id)`.
- Unicidad `(tenant_id, sale_id)` cuando hay venta.
- El hash incluye ambiente, voucher explícito y payload canónico.
- Repetir el mismo `external_id` y contenido devuelve la misma factura.
- Repetir el `external_id` con otro contenido devuelve `409 idempotency_conflict`.

Referencia fiscal única:

```text
(environment, arca_cuit, point_of_sale, voucher_type, voucher_number)
```

### 6.9 Identificación de consumidor final

Si el total es igual o superior a `ARCA_CONSUMER_FINAL_IDENTIFICATION_THRESHOLD` y el receptor sigue como consumidor final genérico (`doc_type=99`, `doc_number=0`), no se emite.

La factura queda en:

```text
receiver_identification_required
```

La venta permanece confirmada. Para continuar se usa el endpoint explícito con el mismo `external_id`, mismo `sale_id`, mismos ítems/fechas, documento real y `voucher_number`. El servicio actualiza la misma factura; no debe crearse otra solicitud.

### 6.10 Cálculo neto e IVA

Los precios se interpretan como finales con IVA incluido. Todos los ítems usan la alícuota e ID configurados en el perfil.

```text
final_item = quantity * final_unit_price
factor     = 1 + default_vat_rate / 100
net_item   = final_item / factor
iva_item   = final_item - net_item
```

Se redondea por ítem a dos decimales con `ROUND_HALF_UP`.

Ejemplo para precio final `121.00` y alícuota `21.00`:

```json
{
  "net_amount": "100.00",
  "iva_amount": "21.00",
  "total_amount": "121.00"
}
```

## 7. API pública de postas_api

Base:

```text
/api/v1/arca
```

Header:

```http
Authorization: Bearer <JWT>
Content-Type: application/json
```

No enviar `tenant_id`, CUIT emisor, ambiente de emisión, certificado, clave o token en endpoints de facturas.

### 7.2 PUT /api/v1/arca/configuration/

Permiso: `OWNER`.

#### Alta o reemplazo de credenciales

Si se envía cualquiera de los campos fiscales principales, deben enviarse juntos:

- `arca_cuit`
- `certificate`
- `private_key`
- `access_token`
- `point_of_sale`
- `automatic_voucher_type`

La actualización parcial del perfil fiscal no está soportada. Para cambiar solamente `concept`, `default_vat_rate`, `default_vat_id`, punto de venta o tipo de comprobante también debe reenviarse el conjunto completo de credenciales y configuración.

Request:

```json
{
  "arca_environment": "development",
  "automatic_invoicing_enabled": false,
  "arca_cuit": "20111111112",
  "certificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
  "private_key": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----",
  "access_token": "<afip-sdk-access-token>",
  "point_of_sale": 3,
  "automatic_voucher_type": 6,
  "concept": 1,
  "default_vat_rate": "21.00",
  "default_vat_id": 5
}
```

La operación ejecuta en orden:

1. Validación de serializer.
2. Entitlement.
3. Validación X.509/clave/CUIT.
4. Cifrado y persistencia con estado `pending`.
5. Validación live contra el ambiente.
6. Respuesta sin secretos.

Respuesta `200`: misma forma que `GET configuration`, con `validation_status: "valid"`.

Si la validación live falla, respuesta `400`:

```json
{
  "code": "fiscal_profile_invalid",
  "message": "ARCA rechazo las credenciales configuradas."
}
```

#### Activar automatización o cambiar ambiente

No es necesario reenviar secretos:

```json
{
  "automatic_invoicing_enabled": true,
  "arca_environment": "development"
}
```

Para habilitarla se exige entitlement, perfil existente, perfil `valid` y `concept=1`.

Errores posibles:

```json
{
  "code": "fiscal_profile_not_valid",
  "message": "El perfil fiscal debe estar validado para activar la automatizacion."
}
```

```json
{
  "code": "automatic_invoicing_requires_products_concept",
  "message": "La facturacion automatica de ventas requiere un perfil con concepto productos."
}
```

Ambos usan HTTP `409`.

### 7.3 DELETE /api/v1/arca/configuration/

Permiso: `OWNER`.

Elimina lógicamente el perfil del ambiente seleccionado y desactiva la automatización. Los secretos se reemplazan por tombstones cifrados.

Respuesta:

```text
204 No Content
```

Si hay facturas no terminales:

```json
{
  "code": "fiscal_profile_in_use",
  "message": "El perfil posee facturas pendientes y no puede eliminarse."
}
```

HTTP `409`.

### 7.5 POST /api/v1/arca/invoices/explicit/

Permiso: cualquier usuario autenticado.

Mismo payload que el endpoint anterior, agregando:

```json
{
  "voucher_number": 184,
  "external_id": "manual-order-2026-000184",
  "receiver": {
    "doc_type": 80,
    "doc_number": "20333333334",
    "iva_condition_id": 1
  },
  "items": [
    {
      "description": "Producto A",
      "quantity": "2.0000",
      "final_unit_price": "121.00"
    }
  ]
}
```

Respuesta `202`: forma común de factura; `voucher_number` ya contiene `184`.

El número explícito debe coincidir con la próxima correlativa disponible cuando el worker procese la factura. De lo contrario finaliza con `correlative_conflict`.

Este endpoint también completa una factura `receiver_identification_required`: debe reutilizar exactamente `external_id`, `sale_id`, fechas e ítems y sólo completar el receptor y número.

## 9. Circuito completo de datos

### 9.1 Alta de configuración

```text
OWNER
  -> PUT /api/v1/arca/configuration/
  -> postas_api toma tenant_id del JWT
  -> verifica entitlement arca_invoicing en Platform
  -> PUT interno del perfil
  -> Platform valida PEM, key, vigencia y CUIT
  -> cifra cert/key/access_token con la Fernet key activa
  -> guarda arca_fiscal_profiles con status=pending
  -> POST interno /validate
  -> Afip SDK obtiene TA y consulta WSFE
  -> Platform marca valid o invalid
  -> postas_api devuelve configuración sin secretos
```

### 9.2 Venta con facturación automática

```text
Usuario confirma venta
  -> SaleCreateSerializer abre transaction.atomic
  -> valida caja, productos, stock y pagos
  -> descuenta stock
  -> crea Sale y SaleDetail
  -> lee TenantConfig
       automatic_invoicing_enabled=false
         -> no crea solicitud fiscal
       automatic_invoicing_enabled=true
         -> crea FiscalOutboxRequest en la misma transacción
  -> commit de venta + detalles + outbox
  -> respuesta de venta inmediata
```

Snapshot guardado en `arca_fiscal_outbox.payload_snapshot`:

```json
{
  "external_id": "1250d487-5d6c-46a0-badb-b389e32359de",
  "sale_id": "1250d487-5d6c-46a0-badb-b389e32359de",
  "actor_id": "7dfd20b8-7558-4c0b-a1df-824edc205cd8",
  "actor_role": "EMPLOYEE",
  "receiver": {
    "doc_type": 99,
    "doc_number": "0",
    "iva_condition_id": 5
  },
  "invoice_date": "2026-07-28",
  "items": [
    {
      "description": "Producto A",
      "quantity": "1.000",
      "final_unit_price": "121.00"
    }
  ]
}
```

Además del payload, la fila fija `tenant_id`, `environment`, `sale_id`, `created_by` y `external_id`.

Campos ARCA dentro de la respuesta inmediata de venta (el objeto conserva además todos los campos normales de `SaleReadSerializer`):

```json
{
  "uuid": "1250d487-5d6c-46a0-badb-b389e32359de",
  "status": "confirmed",
  "invoice_status": "pending",
  "invoice_tracking_id": "1250d487-5d6c-46a0-badb-b389e32359de"
}
```

La venta no espera a ARCA y no se revierte si Platform, Afip SDK o ARCA están caídos.

El `invoice_status` embebido en la venta representa el estado local conocido por la outbox. El seguimiento fiscal canónico, incluido el CAE final, se realiza por `GET /api/v1/arca/invoices/by-external-id/{invoice_tracking_id}/`.

### 9.3 Entrega de outbox a Platform

```text
ArcaOutboxWorker
  -> selecciona una fila due con FOR UPDATE SKIP LOCKED
  -> pending/retrying/sending stale -> sending
  -> incrementa attempt_count y fija locked_at
  -> POST interno /invoices/{environment}/automatic
  -> Platform valida token/source/TLS/tenant/entitlement/perfil
  -> crea arca_invoices y arca_invoice_items idempotentemente
  -> outbox pasa a sent y guarda platform_invoice_id
```

Si Platform no responde:

- La venta queda confirmada.
- La outbox pasa a `retrying`.
- `invoice_status` queda `platform_pending`.
- Se reutilizan `tenant_id`, `environment`, `external_id` y el mismo snapshot.
- Tras agotar cinco intentos pasa a `failed`.

### 9.4 Emisión en Platform

```text
ArcaInvoiceWorker
  -> reclama arca_invoices due con FOR UPDATE SKIP LOCKED
  -> carga el perfil exacto del tenant y ambiente
  -> status=processing, incrementa attempt_count y persiste lease
  -> descifra cert/key/access_token
  -> crea cliente Afip SDK con CUIT y production derivado
  -> si ya hay voucher_number y es reintento:
       consulta getVoucherInfo del mismo comprobante
       si tiene CAE -> adopta resultado y termina approved
       si consulta es incierta -> no reemite
  -> adquiere advisory lock por environment/CUIT/POS/tipo
  -> consulta getLastVoucher
  -> calcula siguiente número
  -> verifica que otra factura no lo tenga reservado
  -> persiste voucher_number antes de llamar a ARCA
  -> createVoucher
  -> normaliza CAE/CodAutorizacion, vencimiento y observaciones
  -> approved o retrying/rejected/failed
```

La reserva durable antes de la llamada externa permite recuperar incluso si el proceso muere después de que ARCA autoriza y antes de guardar la respuesta.

### 9.5 Seguimiento

El frontend utiliza `invoice_tracking_id` como `external_id`:

```http
GET /api/v1/arca/invoices/by-external-id/{invoice_tracking_id}/
```

Se recomienda polling con backoff hasta un estado terminal:

- `approved`
- `rejected`
- `failed`
- `quarantined`
- `receiver_identification_required`

### 9.6 Emisión explícita

```text
Usuario autenticado
  -> POST /api/v1/arca/invoices/explicit/
  -> postas_api deriva tenant/actor/ambiente
  -> Platform persiste voucher_number explícito
  -> worker valida correlativa y emite
  -> seguimiento por external_id
```

### 9.7 Receptor obligatorio

```text
Factura automática supera umbral sin documento
  -> Platform guarda receiver_identification_required
  -> venta sigue confirmed
  -> usuario obtiene documento y próxima correlativa
  -> POST explícito con mismo external_id y sale_id
  -> Platform permite cambiar sólo receiver y voucher_number
  -> misma arca_invoice vuelve a pending
  -> worker emite y obtiene CAE
```

## 10. Estados y reintentos

### 10.1 Outbox de postas_api

| Estado | Significado |
| --- | --- |
| `pending` | Creada junto con la venta. |
| `sending` | Reclamada por un worker. |
| `retrying` | Falló la entrega a Platform y tiene próximo intento. |
| `sent` | Platform aceptó idempotentemente la factura. |
| `failed` | Se agotaron los intentos de entrega. |

Un lock `sending` con más de cinco minutos se considera stale y puede recuperarse.

### 10.2 Factura en Platform

| Estado | Terminal | Significado |
| --- | --- | --- |
| `pending` | No | Persistida y lista para el worker. |
| `processing` | No | Reclamada y con lease. |
| `retrying` | No | Error retryable con próximo intento. |
| `receiver_identification_required` | Sí operativamente | Requiere completar receptor por flujo explícito. |
| `approved` | Sí | ARCA autorizó y se persistió CAE. |
| `rejected` | Sí | ARCA o la correlativa rechazaron la solicitud. |
| `failed` | Sí | Error retryable agotado o perfil inválido. |
| `quarantined` | Sí | Error interno inesperado del worker. |

### 10.3 Cronograma

La solicitud queda disponible inmediatamente (`0`). Los reintentos posteriores se programan a `1`, `10`, `30` y `60` minutos. El quinto intento fallido termina en `failed`.

## 11. Errores relevantes

| Código | HTTP habitual | Acción |
| --- | --- | --- |
| `feature_not_enabled` | 403 | Habilitar `arca_invoicing` para el plan/tenant. |
| `fiscal_profile_not_found` | 404 | Configurar el perfil del ambiente. |
| `fiscal_profile_not_valid` | 409 | Corregir y validar credenciales. |
| `invalid_credentials` | 422 | Revisar PEM, key, vigencia y CUIT. |
| `credential_keyring_unavailable` | 503 | Restaurar keyring e ID activo. |
| `fiscal_profile_invalid` / rechazo por producción deshabilitada | 400 | Habilitar el guard sólo en una instancia productiva autorizada y volver a validar. |
| `idempotency_conflict` | 409 | Reutilizar exactamente el payload original o usar otro ID para otra operación. |
| `fiscal_reference_conflict` | 409 | No reutilizar número fiscal reservado. |
| `automatic_invoicing_requires_products_concept` | 409 | Usar concepto 1 o emisión manual. |
| `service_dates_required` | 422 | Informar las tres fechas. |
| `receiver_identification_required` | 202 con estado | Completar misma factura explícitamente. |
| `explicit_voucher_required` | 409 | Usar endpoint explícito y voucher. |
| `sequence_busy` | Estado retrying | Esperar; otra solicitud tiene la correlativa reservada. |
| `correlative_conflict` | Estado rejected | Consultar última correlativa y revisar número explícito. |
| `arca_timeout` | Estado retrying | No reemitir manualmente; el worker consultará el mismo voucher. |
| `arca_unavailable` | Estado retrying/failed | Revisar conectividad y dejar actuar los reintentos. |
| `arca_auth_error` | Estado rejected/invalid | Revisar token, certificado, autorización y ambiente. |
| `arca_rejected` | Estado rejected | Revisar mensaje/observaciones fiscales. |
| `invoice_not_found` | 404 | Verificar tenant y referencia. |

También pueden aparecer:

- `401`: JWT ausente o inválido en API pública.
- `403`: rol insuficiente, source/token interno inválido o TLS requerido.
- `422`: serializer/Pydantic rechazó el request.
- `502`: Platform devolvió JSON inválido al proxy.
- `503`: configuración interna incompleta o conexión imposible.
- `504`: timeout del cliente `postas_api -> Platform`.

## 13. Rotación de credenciales

### 13.1 Rotar la Fernet master key

1. Generar una nueva Fernet key.
2. Agregarla a `ARCA_CREDENTIAL_MASTER_KEYS` sin retirar las anteriores.
3. Cambiar `ARCA_CREDENTIAL_ACTIVE_KEY_ID`.
4. Reiniciar API y worker.
5. Ejecutar `POST /profiles/rotate-keyring` por tenant.
6. Confirmar `credential_key_id`, `credentials_rotated_at` y `rotated_profiles`.
7. Buscar perfiles que aún referencien la clave anterior.
8. Retirarla sólo cuando el conteo sea cero.

Si se retira antes, esos perfiles no podrán descifrarse.

### 13.2 Rotar certificado, private key o access token

Usar `PUT /api/v1/arca/configuration/` con el conjunto completo. No puede reemplazarse el perfil mientras haya facturas no terminales.

La actualización vuelve el perfil a `pending` y ejecuta validación live antes de responder como válido.

## 14. Recuperación operativa

### 14.1 Timeout incierto

No crear otra factura ni cambiar `external_id`. El número ya fue reservado. El worker consultará `getVoucherInfo(voucher_number, point_of_sale, voucher_type)`:

- Si encuentra CAE, lo adopta sin reemitir.
- Si la consulta falla, reintenta la consulta y no emite.
- Sólo si ARCA confirma “no encontrado” vuelve a intentar `createVoucher` para ese mismo número.

### 14.2 Outbox failed

1. Verificar conectividad `postas_api -> Platform`.
2. Verificar token, source y TLS.
3. Consultar si Platform ya tiene la factura por `external_id`.
4. No generar otro ID para la misma venta.
5. Corregir el problema y reprogramar la fila de outbox de forma controlada.

### 14.3 Quarantined

1. Revisar logs por `invoice_id`.
2. Inspeccionar `request_payload`, `voucher_number`, `last_error_code` y respuesta persistida.
3. Si hay número reservado, consultar el mismo comprobante antes de cambiar estado.
4. Resolver el bug interno antes de reactivar la fila.

### 14.4 Perfil vencido o inválido

1. Desactivar automatización si el problema no será inmediato.
2. Esperar/resolver solicitudes no terminales.
3. Reemplazar certificado/clave/token completos.
4. Validar en el mismo ambiente.
5. Reactivar automatización.
